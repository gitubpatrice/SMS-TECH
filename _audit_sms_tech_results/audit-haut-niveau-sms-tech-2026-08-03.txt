C3 — 🔴 CRITIQUE — CONFIRMÉ — Le refus « code panique = PIN » n'a pas de symétrique
     côté PIN : enfermement définitif
--------------------------------------------------------------------------------
Localisation : data/src/main/java/com/filestech/sms/security/AppLockManager.kt:108-119
Le côté correct : AppLockManager.kt:164-180
Famille      : 3 (asymétrie) + 1 (garde mal visé — il ne couvre qu'un sens)
Trouvé indépendamment par l'orchestrateur et par un agent.

CE QUI EST EN PLACE
`setPanicCode()` refuse un code identique au PIN, avec une justification explicite
en 5 lignes (AppLockManager.kt:153-157) :

    « attemptUnlock évalue le code panique AVANT le PIN. Un code identique ferait
      systématiquement gagner le leurre : l'utilisateur n'aurait plus AUCUN moyen
      d'ouvrir son application normalement, et le coffre lui deviendrait
      inaccessible à lui aussi. C'est un enfermement définitif, pas une gêne. »

LE DÉFAUT
`setPin()` ne fait AUCUNE vérification symétrique. Il ne lit jamais
`panicSnapshot()`, ne refuse rien, et n'efface pas le code panique :

    suspend fun setPin(newPin: CharArray): Unit = withContext(io) {
        val salt = kdf.newSalt()
        val iters = kdf.calibrate()
        try {
            val hash = kdf.derive(newPin, salt, iters)
            securityStore.setPinHash(salt, hash, iters)
        } finally { newPin.wipe() }
        settings.update { … lockMode = LockMode.PIN … }
        _state.value = LockState.Locked
    }

LE SCÉNARIO
Code panique = 1234, PIN = 9999. L'utilisateur change son PIN (le picker rouvre le
dialogue de saisie même quand le mode est déjà PIN — SettingsScreen.kt:654-662) et
choisit 1234, la valeur qu'il a mémorisée.
Chaîne : SettingsScreen.kt:733 → SettingsViewModel.kt:133 → AppLockManager.setPin.

À partir de là, `attemptUnlock` (AppLockManager.kt:236-244) évalue le panique en
premier : le seul secret que l'utilisateur connaît ouvre systématiquement le
LEURRE. Plus aucun accès à sa vraie session ni à son coffre.

C'est très exactement l'enfermement définitif que le refus `SameAsPin` documente
comme inacceptable — atteint par la porte d'à côté.

ACTION
Dans `setPin`, lire `securityStore.panicSnapshot()` et refuser si le candidat
correspond (nouveau `SetPinOutcome`, sur le modèle de `PanicCodeOutcome`) ; ou
effacer le code panique et le dire explicitement à l'utilisateur.
EFFORT : Rapide (< 1 h)

H2 — 🟠 HAUTE — CONFIRMÉ — Un Intent forgeable ouvre n'importe quelle conversation
--------------------------------------------------------------------------------
Localisation : app/src/main/java/com/filestech/sms/MainActivity.kt:455-479
               app/src/main/AndroidManifest.xml:142-148
Famille      : 1 (garde mal visé) + 3 (asymétrie avec SafetyCallIntentToken)

`MainActivity` est légitimement `exported="true"` (rôle SMS) et sans permission.
Une app tierce peut donc l'atteindre par Intent EXPLICITE avec n'importe quelle
action, indépendamment des `<intent-filter>`.

`ACTION_OPEN_CONVERSATION` ("com.filestech.sms.OPEN_CONVERSATION") et
`EXTRA_CONVERSATION_ID` ("conversationId") sont des constantes publiques
(IncomingMessageNotifier.kt:354, 357). Le handler ne vérifie AUCUNE origine :
ni jeton, ni PendingIntent de rappel, ni permission de signature.

C'est une asymétrie nette : l'équipe a construit la bonne défense
(`SafetyCallIntentToken` — nonce SecureRandom, `consume()` mono-usage,
MainActivity.kt:419-426) mais ne l'a appliquée qu'à UNE des quatre actions
internes routées par MainActivity.

SCÉNARIO — app tierce sans aucune permission :
    startActivity(new Intent()
        .setComponent(new ComponentName("com.filestech.sms","com.filestech.sms.MainActivity"))
        .setAction("com.filestech.sms.OPEN_CONVERSATION")
        .putExtra("conversationId", 7L));
Les ids sont des Long Room séquentiels : énumération triviale. Combiné à H1, si la
conversation est dans le Coffre, son contenu s'affiche sans le second facteur.
Si l'app est verrouillée, le pending reste armé 30 s (PendingNavHolder.kt:117) et
se déclenche au déverrouillage suivant.

LIMITE HONNÊTE : l'app tierce ne peut pas LIRE l'écran (FLAG_SECURE par défaut).
Le gain est l'affichage forcé du contenu protégé — pertinent en contexte de
contrainte ou d'épaule, qui est le modèle de menace du Coffre.

ACTION : garde `inVault` sur la route Thread (corrige aussi H1) + jeton mono-usage
sur `ACTION_OPEN_CONVERSATION`, sur le modèle de `SafetyCallIntentToken`.
EFFORT : Moyen

H4 — 🟠 HAUTE — CONFIRMÉ — Liste noire : 9 chiffres à la réception, 8 à la

Localisation : data/src/main/java/com/filestech/sms/data/sync/TelephonySyncManager.kt:221-232

La v1.25.4 a unifié la clé de liste noire sur `blockKey()` = 9 chiffres, en
documentant précisément pourquoi 8 ne suffit pas (StringExt.kt:73-79) : « s'arrêter
à 8 amputait le premier chiffre, celui-là même qui sépare un mobile 06… d'un 07… ».
`blockKey()` est utilisé par BlockedNumberRepositoryImpl, ConversationRepositoryImpl
(badge « Bloqué ») et SmsDeliverReceiver.

Les deux chemins de synchronisation sont restés à 8 :

    val blockedSuffixes = (roomBlocked.asSequence() + systemBlocked.asSequence())
        .map { it.phoneSuffix8() }.filter { it.isNotEmpty() }.toHashSet()
    …
    else page.filter { it.entity.address.phoneSuffix8() !in blockedSuffixes }

Or `roomBlocked` contient DÉJÀ des `blockKey()` (colonne `normalized_number` depuis
la v1.25.4). Les re-tronquer à 8 réintroduit exactement la confusion supprimée.

DEUX EFFETS, opposés et tous deux faux :

  (1) PERTE DE DONNÉES RÉELLE — `0612345678` bloqué produit la clé `612345678`,
      ramenée à `12345678`. Les SMS d'un contact NON BLOQUÉ `0712345678` donnent
      le même suffixe et sont écartés de l'import. Le curseur avance quand même
      (TelephonySyncManager.kt:259-262) : ces messages ne seront JAMAIS importés.
      Silencieux et définitif. Sur un premier lancement, c'est tout l'historique
      de ce correspondant qui disparaît.

  (2) BLOCAGE INOPÉRANT — une clé alphanumérique (« sfr ») donne
      `phoneSuffix8() == ""`, éliminée par le `.filter { it.isNotEmpty() }`.
      Les SMS d'un expéditeur alphanumérique bloqué sont importés malgré le
      blocage — la divergence même que la v1.25.4 disait rendre
      « structurellement impossible ».

================================================================================

1. LA QUALITÉ D'INTENTION EST TRÈS HAUTE. Chaque garde porte un commentaire qui

      Variante suivante envisagée — laisser `findOrCreate` créer une conversation
      jumelle hors coffre : `thread_id` porte un index UNIQUE et les créations
      utilisent `threadId = 0L` avec `OnConflictStrategy.REPLACE` ⇒ multiplier ces
      insertions aurait pu ÉCRASER EN CASCADE une conversation locale déjà à 0.
      **`findOrCreate` n'a donc pas été touché.** Le masquage en couche données
      suffit à fermer la fuite, et il réutilise un chemin que l'UI gère déjà
      (tous les accès à `conversation` sont en appel sûr, tous les chemins d'envoi
      gardent `conversation == null`) — vérifié avant application.

  CONSÉQUENCE À CONNAÎTRE : ouvrir un fil du Coffre sans être passé par l'écran
  Coffre (ex. « Nouveau message » vers ce contact) affiche désormais un fil VIDE
  tant que le second facteur n'a pas été franchi dans la session. C'est le
  comportement voulu, mais c'est un changement visible.

ÉTAGE 3-BIS — LA REVUE INDÉPENDANTE A TROUVÉ 1 RÉGRESSION + 3 DÉFAUTS DANS MES

Une revue adversariale a été relancée SUR les correctifs de l'étage 3, une fois
ceux-ci déjà installés sur le téléphone principal. Elle a rapporté quatre défauts
réels, tous vérifiés dans le code avant correction. C'est la 8ᵉ fois d'affilée que

  🔴 RÉGRESSION INTRODUITE PAR H1 — le fil du Coffre se vidait au moindre
     passage en arrière-plan, et « Envoyer » devenait muet.
     `lockVaultOnLeave` vaut `true` PAR DÉFAUT (AppSettings.kt:176) et
     `AutoLockObserver` referme le Coffre IMMÉDIATEMENT à chaque `onStop`, AVANT
     tout délai (AutoLockObserver.kt:95-98, vérifié). Donc : bascule d'application,

     1211, 1284) : le bouton ne faisait plus rien, sans le moindre message.
     Avant H1, `conversation == null` n'était atteignable qu'en session leurre —
     état où l'écran est déjà gardé en amont. C'était donc un état NOUVEAU, et
     fréquent.
     CORRECTIF : nouveau `ConversationRepository.observeVaultHidden(id)` qui
     distingue « masqué par le Coffre » de « conversation inexistante », et
     `ThreadScreen` ressort du fil au lieu d'afficher un écran mort.
     ⚠️ La sortie est différée par `withResumed` : la fermeture du Coffre survient
     pendant `onStop`, donc dépiler à cet instant viserait l'écran voisin —
     exactement le dépilement parasite corrigé en v1.25.4.
     ⚠️ `observeVaultHidden` rend `false` en session leurre : le fil doit y rester
     indiscernable d'une conversation inexistante, surtout pas déclencher une
     navigation qui trahirait qu'il y a quelque chose à cacher.

     `parsed.from?.string` porte le suffixe passerelle `/TYPE=PLMN`. `blockKey()`

     correspondance possible avec la clé stockée. La garde ne bloquait RIEN.
     CORRECTIF : `stripMmsAddressSuffix` remonté dans `core/ext/StringExt.kt`

     dossier). Mon propre commentaire affirmait « le nettoyage reste assuré par le
     finally » : vrai du PDU, FAUX du média.
     CORRECTIF : garde remontée avant tout décodage et toute écriture.
